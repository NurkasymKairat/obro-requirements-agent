### 1. Противоречие: Критерий приёмки (Критерии приёмки, строка 51) противоречит функциональному требованию П-3. Согласно требованию П-3, «Сумма переводов...

**F-026** · критично · противоречие · подтверждено · R-008, R-021
- Суть: Критерий приёмки (Критерии приёмки, строка 51) противоречит функциональному требованию П-3. Согласно требованию П-3, «Сумма переводов клиента не превышает 500 000 ₸ в сутки. При превышении лимита клиенту показывается сообщение». В критерии приёмки заданы условия: за сутки уже переведено 250 000 ₸, клиент совершает перевод на 300 000 ₸. Итоговая сумма переводов за сутки составляет 250 000 + 300 000 = 550 000 ₸, что превышает суточный лимит 500 000 ₸. По правилам требования перевод должен быть отклонён с выводом сообщения, однако ожидаемый результат критерия утверждает: «Перевод выполнен, остаток счёта списания 100 000 ₸».
- Цитата 1: «Сумма переводов клиента не превышает 500 000 ₸ в сутки. При превышении лимита клиенту показывается сообщение.»
  Место: Часть A. Постановка задачи › Функциональные требования, строка 26
- Цитата 2: «За сутки переведено 250 000 ₸, на счёте списания 400 000 ₸ | Перевести 300 000 ₸ | Перевод выполнен, остаток счёта списания 100 000 ₸»
  Место: Часть A. Постановка задачи › Критерии приёмки, строка 51
- Критерий: согласованность (consistent); стандарт: ISO/IEC/IEEE 29148 п. 5.2.6
- Объединено: F-014 — Одно и то же противоречие: ожидаемый результат критерия приёмки (успешный перевод при превышении суточного лимита) противоречит ограничению в 500 000 ₸ из требования П-3.
- Как исправить: Привести ожидаемый результат критерия приёмки (Критерии приёмки, строка 51) в соответствие с требованием П-3: «Перевод отклонён, клиенту показано сообщение о превышении суточного лимита (500 000 ₸), остаток на счёте списания не изменился и составляет 400 000 ₸».

### 2. Противоречие: Требование П-2 части A гарантирует выполнение перевода без комиссии при любых валютах счетов, тогда как в части B в описании поля ответа...

**F-033** · высокая · противоречие · подтверждено · R-007, R-039
- Суть: Требование П-2 части A гарантирует выполнение перевода без комиссии при любых валютах счетов, тогда как в части B в описании поля ответа fee установлена комиссия за конвертацию в размере 0,5 % суммы перевода при разных валютах счетов. Если бэкенд реализует списание комиссии согласно спецификации API, а веб-интерфейс будет спроектирован по требованиям части A как бесперебойный и бесплатный перевод, клиент столкнется с непредусмотренным списанием комиссии, а экраны подтверждения и квитанции будут противоречить друг другу.
- Цитата 1: «Перевод выполняется без комиссии при любых валютах счетов.»
  Место: Часть A. Постановка задачи › Функциональные требования, строка 25
- Цитата 2: «`fee` | number | Комиссия за конвертацию: 0,5 % суммы при разных валютах счетов»
  Место: Часть B. API › Поля ответа, строка 92
- Критерий: согласованность (consistent); стандарт: ISO/IEC/IEEE 29148 п. 5.2.6
- Как исправить: Согласовать условие о комиссии: если перевод строго бесплатный во всех случаях, изменить описание поля fee в части B на «Комиссия за перевод; всегда 0» либо удалить поле fee; если комиссия за конвертацию должна взиматься, скорректировать П-2 в части A, указав: «При совпадении валют перевод выполняется без комиссии; при конвертации валют взимается комиссия 0,5 % суммы».

### 3. Противоречие: Требование П-2 части A задает минимальную сумму перевода в 100 ₸, тогда как спецификация API в части B допускает сумму перевода начиная...

**F-035** · высокая · противоречие · подтверждено · R-006, R-036
- Суть: Требование П-2 части A задает минимальную сумму перевода в 100 ₸, тогда как спецификация API в части B допускает сумму перевода начиная от 1. При реализации разных правил валидации на клиенте и сервере запросы на перевод сумм от 1 до 99 будут либо ошибочно пропускаться API в обход бизнес-требования, либо блокироваться клиентским интерфейсом без единого контракта с бэкендом.
- Цитата 1: «Сумма перевода — от 100 ₸ до остатка на счёте списания.»
  Место: Часть A. Постановка задачи › Функциональные требования, строка 25
- Цитата 2: «`amount` | number | Да | 1–500 000, два знака после запятой | Сумма в валюте счёта списания»
  Место: Часть B. API › Параметры запроса, строка 84
- Критерий: согласованность (consistent); стандарт: ISO/IEC/IEEE 29148 п. 5.2.6
- Как исправить: Согласовать нижнюю границу суммы перевода: изменить ограничение параметра amount в таблице параметров части B на «100–500 000, два знака после запятой» (с учетом эквивалента в валюте списания) либо изменить П-2 в части A, если разрешен перевод от 1 ₸.

### 4. Противоречие: В спецификации параметров запроса части B обязательное поле счета списания названо fromAccount, а в примере curl-запроса (Общие...

**F-037** · высокая · противоречие · подтверждено · R-027, R-034
- Суть: В спецификации параметров запроса части B обязательное поле счета списания названо fromAccount, а в примере curl-запроса (Общие параметры, строка 68) то же поле названо sourceAccount. Несоответствие наименования приведет к ошибкам при интеграции фронтенда и бэкенда (ошибка 400 из-за отсутствия обязательного поля).
- Цитата 1: «`fromAccount` | string | Да | 20 символов | Счёт списания»
  Место: Часть B. API › Параметры запроса, строка 82
- Цитата 2: «"sourceAccount":"KZ01"»
  Место: Часть B. API › Общие параметры, строка 68
- Цитата 3: «`curl -X POST "$BASE/transfers/own" -d '{"requestId":"a1","sourceAccount":"KZ01","toAccount":"KZ02","amount":1500.50}'`»
  Место: Часть B. API › Общие параметры, строка 68
- Критерий: согласованность (consistent); стандарт: ISO/IEC/IEEE 29148 п. 5.2.6
- Объединено: F-015 — Один и тот же дефект расхождения наименования поля счета списания: fromAccount в таблице параметров и sourceAccount в примере вызова API.
- Как исправить: Унифицировать имя поля в части B: заменить в примере (Общие параметры, строка 68) "sourceAccount":"KZ01" на "fromAccount":"KZ01".

### 5. Противоречие: В шаге 4 логики работы API указано, что при повторном запросе с тем же requestId сервис возвращает результат первого запроса без...

**F-038** · высокая · противоречие · подтверждено · R-031, R-043, R-046
- Суть: В шаге 4 логики работы API указано, что при повторном запросе с тем же requestId сервис возвращает результат первого запроса без повторного списания (прозрачная идемпотентность с успехом). Однако в разделе статусов и примерах ошибок указано, что на повторный запрос возвращается HTTP-код 409 с телом {"message":"Повторный запрос"}. Разработчики бэкенда и фронтенда реализуют несовместимое поведение: клиентское приложение при повторной отправке запроса после таймаута сети получит ошибку 409 Конфликт вместо успешного подтверждения операции.
- Цитата 1: «4. При повторном запросе с тем же `requestId` вернуть результат первого запроса без повторного списания.»
  Место: Часть B. API › Логика работы, строка 74
- Цитата 2: «**409.** Запрос с таким `requestId` уже был обработан.»
  Место: Часть B. API › Статусы, строка 99
- Цитата 3: «{"message":"Повторный запрос"}»
  Место: Часть B. API › Статусы › 409. Конфликт, строки 112–114
- Критерий: согласованность (consistent); стандарт: ISO/IEC/IEEE 29148 п. 5.2.6
- Объединено: F-018, F-025 — Единая первопричина: противоречие между шагом 4 алгоритма (возврат результата первого запроса без повторного списания) и спецификацией ошибки 409 с телом «Повторный запрос».
- Как исправить: Зафиксировать единый контракт обработки идемпотентных запросов: исключить статус 409 и пример (409. Конфликт, строки 112–114), подтвердив возврат сохраненного ответа первого запроса (HTTP 200 с телом операции), либо скорректировать шаг 4 логики работы, указав на возврат HTTP 409 при повторном использовании requestId.
