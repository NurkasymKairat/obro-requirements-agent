# Агент проверки требований

## 1. Что это

Консольный агент статической проверки документа требований до начала разработки. Читает документ
(PDF, Markdown, TXT, DOCX), выделяет требования, проверяет каждое требование и набор целиком по
ISO/IEC/IEEE 29148:2018 (п. 5.2.5, 5.2.6) и IEEE 830-1998 (п. 4.3). Запускается одной командой,
на выходе — отчёт на русском, где каждое замечание привязано к цитате и месту документа.

## 2. Быстрый старт

Нужен Python 3.11 или новее. Команды выполняются из корня репозитория.

```
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Windows (PowerShell): `py -3.12 -m venv .venv`, `.venv\Scripts\Activate.ps1`, `copy .env.example .env`.

Ключ Gemini:

1. Откройте https://aistudio.google.com/apikey, войдите аккаунтом Google, нажмите «Create API key».
2. Впишите ключ в файл `.env` в корне репозитория: `GEMINI_API_KEY=ваш_ключ`. Остальные строки можно не трогать.

Запуск:

```
python -m agent docs/requirements.md reports/report.md
```

Первый аргумент — путь к проверяемому документу, второй — путь к отчёту (по умолчанию
`reports/report.md`). Документ организаторов в этот репозиторий не включён: он берётся из репозитория
задания https://github.com/BCC-HUB/ai-requirements-validator-task — положите его в `docs/requirements.md`
или укажите свой путь.
Проверить запуск без него можно на примере из репозитория:
`python -m agent eval/sample_other.md reports/sample.md`.

Результат:

- `reports/report.md` — отчёт: паспорт прогона, главное (до пяти самых сильных дефектов), нарезка
  требований, проверка каждого требования, проверка набора, сводка, итог;
- `reports/report.json` — те же данные в машиночитаемом виде, пишется рядом с отчётом.

Папка `reports/` создаётся сама. Ход прогона печатается в консоль. Если прогон прервался, та же команда
продолжит с последнего успешного вызова: ответы модели кешируются в `.cache/llm`.

## 3. Как устроено

Документ передаётся в каждый вызов модели целиком. Шаги идут в таком порядке:

| Шаг | Кто выполняет | Что делает |
| :--- | :--- | :--- |
| `extract` | модель, 1 вызов | Нарезает документ на требования с дословными цитатами |
| `rules` | код | Пустые поля шаблона, незаполненные чек-листы, метод и коды HTTP, типы полей, единицы измерения, размытые слова без чисел |
| `individual` | модель, пачки по 16 требований | Проверяет каждое требование по свойствам п. 5.2.5 |
| `cross_acceptance` | модель, 1 вызов | Сверяет требования с критериями приёмки; заполняет таблицу количественных требований |
| `parts_goals` | модель, 1 вызов | Сверяет части документа между собой; заполняет таблицу «цель — требование» |
| `review` | модель, 1 вызов | Сливает дубли, уточняет степень, ищет вторую сторону противоречий, оспаривает спорное, ищет пропуски |

Модель даёт содержание: требования, замечания, цитаты, строки таблиц. Остальное делает код:

- **Порядок.** `individual`, `cross_acceptance` и `parts_goals` идут параллельно (до `AGENT_CONCURRENCY`
  вызовов, по умолчанию 3), `review` — после них.
- **Проверка цитат.** Каждая цитата из ответа модели ищется в тексте документа. Не найдена — замечание
  отбрасывается, это записывается в журнал прогона.
- **Замечания из таблиц.** По таблицам количественных требований и целей замечания собирает код, а не модель.
- **Пороги серьёзности.** Подтверждённое противоречие с цитатами обеих сторон — не ниже «высокой»;
  противоречие требования с критерием приёмки или между требованиями одного сценария — «критично».
  Проход `review` меняет степень не больше чем на одну ступень и только с причиной из закрытого списка.
  Противоречие с одной цитатой и оспоренное замечание получают статус «возможное», а не удаляются.
- **Вердикт.** Есть подтверждённый критичный дефект — начинать нельзя; есть дефект высокой степени —
  можно после исправлений; иначе можно. Блок «Главное» тоже отбирает код.

Для документа организаторов (67 требований) прогон делает 9 вызовов модели: 1 + 5 + 1 + 1 + 1.
Время — около 5–6 минут, дольше всего идут сверки и `review`, где модель рассуждает.

## 4. Модели

По умолчанию — `gemini-3.8-flash`, запасные — `gemini-3.6-flash` и `gemini-3.5-flash`. Для OpenAI задайте
в `.env` строки `LLM_PROVIDER=openai` и `OPENAI_API_KEY=...`; модель по умолчанию — `gpt-6-sol`.
Все настройки с пояснениями — в `.env.example`.

Сдаваемый отчёт получен на платном ключе Gemini. На бесплатном ключе агент проверен отдельно: прогон
доходит до конца, при перегрузке основной модели агент уходит на запасную, и замечаний при этом может
быть меньше (см. таблицу в разделе 6). Модель каждого прохода указана в паспорте отчёта. Лимит
бесплатного уровня — 20 запросов в день на модель, прогон занимает 9; повторы при сбоях добавляют вызовы.

Поведение при сбоях:

| Ситуация | Что делает агент |
| :--- | :--- |
| 503, 429 по минутному лимиту, обрыв сети | До трёх повторов с паузой, затем следующая модель из `GEMINI_FALLBACK_MODELS` до конца прогона |
| 429, исчерпана дневная квота модели | Сразу следующая модель |
| Запрос завис: 90 с (`AGENT_TIMEOUT`) или 360 с для проходов с рассуждением (`AGENT_TIMEOUT_THINKING`); ответ 504 | Один повтор, затем следующая модель |
| 403 «The Gemini API free tier is not available for this project» | Остановка: нужен ключ из нового проекта AI Studio под личным аккаунтом Google либо включённая оплата |
| 402, закончился баланс | Остановка: пополните баланс и запустите ту же команду |

Если прогон оборвался, отчёт всё равно записывается, но помечается как неполный, вердикт не выносится.

Коды выхода: 0 — полный прогон; 1 — внутренняя ошибка (подробности с `AGENT_DEBUG=1`); 2 — ошибка настроек
или входного файла; 3 — все модели недоступны; 4 — сбой одного из проходов; 5 — закончился баланс;
6 — проекту недоступен бесплатный тариф; 130 — прервано пользователем.

## 5. Веб-версия

https://hack.obroai.com — тот же агент в браузере, работает на GPT. Пример отчёта открыт всем; загрузка
своего документа — по логину и паролю из формы подачи.

Локально: `pip install -r requirements-web.txt`, сборка фронта `cd web && npm ci && npm run build`
(Node.js 20 или новее), запуск `python -m api`, адрес http://127.0.0.1:8000.

## 6. Результаты

Сверка с эталоном дефектов: `python eval/score.py reports/report.json`. Эталон составлен командой:
30 дефектов документа организаторов (`eval/golden.yaml`), из них 16 — ядро: противоречия, непроверяемые
и неполные требования, блокирующие разработку. Второй документ — собственное ТЗ из другой области
(`eval/sample_other.md`, 16 дефектов, ядро 15) для проверки, что агент не настроен под один документ.
Эталон в промпты не попадает.

| Документ | Модель | Ядро | Все дефекты | Выдуманных цитат | Вызовов | Время |
| :--- | :--- | :---: | :---: | :---: | :---: | :---: |
| Документ организаторов, Markdown (сдаваемый отчёт) | gemini-3.8-flash | 16/16 | 25/30 | 0 | 9 | 5 мин 2 с |
| Документ организаторов, PDF | gemini-3.8-flash | 16/16 | 27/30 | 0 | 9 | 5 мин 0 с |
| Второй документ | gemini-3.8-flash | 15/15 | 16/16 | 0 | 7 | 5 мин 19 с |
| Документ организаторов, Markdown | gpt-6-sol | 16/16 | 28/30 | 0 | 9 | 2 мин 56 с |
| Документ организаторов, Markdown, бесплатный ключ | gemini-3.6-flash (запасная после 503 основной) | 15/16 | 22/30 | 0 | 14 | 7 мин 24 с |

На `gemini-3.8-flash` по Markdown-версии в трёх прогонах ядро 16/16 и один и тот же список критичных
дефектов. В сдаваемом отчёте 35 замечаний, 10 из них не входят в эталон и требуют
ручной оценки. Прогон на бесплатном ключе сделан более ранней версией агента.

## 7. Ограничения

- Результат зависит от модели. На запасной модели найдено меньше: 22/30 против 25/30, ядро 15/16.
  Состав некритичных замечаний между прогонами может отличаться: на PDF-версии два прогона дали 24/30 и 27/30.
- Полнота измерена на двух документах по эталону, который составила сама команда. На других ТЗ она
  не измерялась; замечания вне эталона на ложные срабатывания проверялись только выборочно.
- В сдаваемом отчёте не найдены пять дефектов эталона из 30 (названия — как в `eval/golden.yaml`):
  - G-30: Ф-2 относит покупку к месяцу по дате совершения, а учитывает только проведённые покупки — не сказано,
    когда и в какой месяц попадает покупка, проведённая позже;
  - G-27: не описаны сбои отправки push — повтор, признак отправки при ошибке, отключённые уведомления на устройстве;
  - G-25: набор не прослеживаем и не ранжирован — нет приоритетов, у НФТ, данных и интеграции нет идентификаторов,
    нет задачи Jira;
  - G-26: терминология не выдержана — порог / лимит / бюджет, учёт расходов / сервис расходов, сервис push /
    сервис уведомлений;
  - G-28: не описано выключение уведомления через API — amount обязателен и при enabled=0, судьба порога не определена.
- Читается только текст: изображения, схемы и сканы без текстового слоя не анализируются. Документ целиком
  передаётся в каждый вызов; на документах заметно больше 70 требований агент не проверялся.
